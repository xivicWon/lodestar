## 2. 범위와 분모 — 무엇으로 recall 을 재는가

정확도 수치는 **분모가 정의될 때만** 의미가 있다. gold 파일은 두 종류이며 섞어 쓰면 안 된다.

| 종류 | `scope.closed` | 의미 | 해당 파일 |
|---|---|---|---|
| **닫힌 범위** | `true` | 그 범위 안의 사실이 **전수 등재**돼 있다. 여기 없는 산출물은 오탐이고, recall 의 분모가 된다. | `l1/db.json` · `l1/code.json` · `pii.json` · `failures.json` |
| **판정표** | `false` | 지목된 케이스에 대한 정오 판정만 한다. **전체 recall 을 주장할 수 없다** — 후보 공간을 전수 열거할 수 없기 때문이다. | `l2/links.json` · `l3/claims.json` · `evl/questions.json` |

- **DB 트랙 닫힌 범위:** `legacy-sample.sql` 파일 **전체**. 테이블 27 · 컬럼 119 · PK 27 · FK 1 · 뷰 1.
- **코드 트랙 닫힌 범위:** 5개 파일 — `provenance/ProvenanceVocab.kt`, `rdb/SchemaModel.kt`, `rdb/SchemaSource.kt`, `rdb/SqlTypeMapping.kt`, `rdb/DdlParser.kt`. 타입 13 · 메서드 10 · 프로퍼티 7 · 호출 11.
  나머지 54개 `.kt` 는 **범위 밖**이다. 범위 밖은 *미측정*이지 *통과*가 아니며, 그 파일들의 추출 품질을 근거로 어떤 주장도 하지 않는다.
- L2 는 컬럼 쌍의 조합이 후보 공간이라 전수 열거가 불가능하다. 따라서 **등재된 케이스에 한해** precision/recall 을 내고, Run Quality Report 에 "케이스 한정" 임을 명시한다.

> **왜 코드 범위를 5개 파일로 좁혔나:** 59개 파일 전부에 대해 사람이 검증한 정답을 만들 수는 없고, 검증되지 않은 정답으로 잰 수치는 정답이 아니라 또 하나의 추정이다. 좁고 확실한 분모가 넓고 모호한 분모보다 낫다 — 넓은 쪽은 항상 "대체로 맞다"로 끝난다(I1 G4).

## 3. 레이어별 Gold Set

### 3.1 L1 — 명시 사실

정답은 **원본에 문자로 존재하는 것**뿐이다. 추론이 한 톨이라도 들어가면 L1 이 아니다.

주요 판정 규칙(전문은 각 파일의 `rules`):

- **R-DB-3** PK 구성 컬럼의 `nullable` 은 `false` 다. SQL 의미상 PK 는 NOT NULL 이며, DDL 에 `NOT NULL` 이 문자로 없다는 이유로 `true` 로 두면 스키마 의미가 틀어진다. *(현 `DdlParser` 는 `NOT NULL` 문자열만 보므로 여기서 어긋난다 — 의도된 관측 지점이다.)*
- **R-CODE-1** 호출은 `(caller, callee)` 쌍으로 **중복 제거**한다. `DdlParser.toTableInfo → unquote` 는 소스에 10번 나오지만 1건이다.
- **R-CODE-2** 표준 라이브러리·Spring·JSqlParser 호출은 등재하지 않으며, 추출돼도 오탐으로 세지 않는다(미측정).
- **R-CODE-5** 컴파일러 생성 멤버(enum `valueOf`, data class `copy` 등)는 어디에도 등재하지 않는다. 소스에 없는 것을 정답으로 요구하면 추출기마다 판정이 갈린다.
- **R-CODE-6** `PROPERTY` 는 **타입 본문에 선언된 것만** 센다(override val · const val 포함). 생성자 파라미터 프로퍼티는 소유 `TYPE` 의 `properties` 로 기록해 중복 계상하지 않고, 프로퍼티가 아닌 생성자 파라미터는 등재하지 않는다. 닫힌 범위에서는 **분모 정의가 곧 측정 결과**이므로 이 규칙 없이는 recall 이 집계 방식에 따라 달라진다.

**음성 항목(`expect: ABSENT`)이 정답셋의 일부다.** 산출하면 오답인 것들을 명시적으로 적어 둔다:

| 항목 | 왜 음성인가 |
|---|---|
| `L1.DB.TABLE.NEG.만` | 한국어 주석 "`CREATE TABLE` 만 처리하므로…" 를 문장으로 오인한 결과. **I1 §1.1 의 "28" 이 정확히 이 오탐이다**(§8) |
| `L1.DB.FK.NEG.TB_ORD_HD.CUST_NO` | 관계는 실재하지만 DDL 에 선언돼 있지 않다. L1 에서 FK 로 잡으면 추론을 명시로 승격한 것(I1 P2). 정답 자리는 L2 INFERRED 다 |
| `L1.CODE.TYPE.NEG.SqlTypeMapping` | 파일명에서 유추한 타입. 소스에 선언이 없다 |

`expect: REPORTED_EXCLUDED` 는 제3의 값이다 — `VW_ORD_SUMMARY` 는 **추출해도 실패, 조용히 건너뛰어도 실패**이며, 제외 사유와 함께 보고해야 통과다(I1 §4.1 오류 가시성).

### 3.2 L2 — 교차소스 링크

이슈가 요구한 다섯 종류를 모두 담았다.

| 종류 | 근거 | 사례 |
|---|---|---|
| 동일이름 | 리포 | `TB_ORD_HD.CUST_NO → TB_CUST_MST.CUST_NO` (양성) · `USE_YN` 4개 테이블 (음성) |
| 오버로드 | 픽스처 | revB `placeOrder(String)` / `placeOrder(String,String)` — 병합하면 오답 |
| 이동 | 픽스처 | `fixture.alpha.OrderService` → `fixture.beta.OrderService` |
| rename | 픽스처 | `PriceCalc` → `PricingCalculator` (본문 동일) |
| 삭제 | 픽스처 | revB 에서 `legacyReport()` 제거 — 소유 타입은 살아 있으므로 **멤버 단독 삭제** |
| 재등장 | 픽스처 | revC 에서 같은 모습으로 복귀 → 정답은 **AMBIGUOUS** |

- **EXTRACTED 가 정답인 링크는 DB 코퍼스 전체에서 단 하나**(`FK_ORD_MEMO`)다. 다른 쌍이 EXTRACTED 로 나오면 그 순간 I1 P2 위반이므로, 이 한 건이 precision 의 기준점이다.
- 이동·rename 은 서로 반대되는 신호 조합을 요구한다. 이동은 이름이 같고 위치가 다르며, rename 은 이름이 다르고 구조가 같다. 여기에 음성(`revA.PriceCalc` ↔ `revC.gamma.PriceCalc` — 이름만 같은 남남)을 붙여 **이름만 보는 구현과 구조만 보는 구현이 모두 걸리도록** 짰다.
- **재등장의 정답이 AMBIGUOUS 인 이유:** 소스만으로는 부활인지 동명의 신규인지 결정할 수 없다. 자동 부활은 사람 확인 없이 확정 라벨을 되살리고(P2 우회), 무조건 신규 처리는 확인 이력을 끊는다(I1 §4.1). **둘 다 오답**이며 해소는 `HUMAN_CONFIRMED` 경로로만 한다.
- **음성 9건**이 등재돼 있다. 양성만으로 잰 precision 은 항상 낙관적으로 나온다.

### 3.3 L3 — Claim 시나리오

L3 계약(P1·P4, 확인 이력 보존)은 한 시점의 값이 아니라 **상태 전이**에 걸려 있다. 그래서 gold 는 항목 목록이 아니라 단계별 시나리오 5개이며, 각 단계에 `mustHold`(전부 성립) / `mustNot`(하나라도 성립하면 실패)를 둔다.

| 시나리오 | 겨냥하는 실패 |
|---|---|
| 정상 | AI 추정을 EXTRACTED 로 승격 · 확인하지 않은 것을 확인됐다고 표시 |
| 변경 | 정정을 **덮어쓰기**로 처리 — 이전 레코드 소실, `supersedes` 누락 |
| 충돌 | 상충 Claim 중 하나를 조용히 버림 · confidence 높은 쪽 자동 채택 (P4) |
| 삭제 | 근거가 사라졌는데 Claim 이 그대로 active (I1 §3.3 전파 미구현) |
| 재등장 | 확정 라벨의 무단 부활 · 확인 이력 소실 |

**판정 대상은 라벨 문구가 아니라 status·evidenceIds·supersedes·validFrom/validTo·확인 이력의 전이다**(R-L3-2). 문구 일치를 요구하면 AI 출력의 표현 차이가 정확도 실패로 오집계된다.

### 3.4 EVL 확장 — answer-shape 층 측정용

EVL 계약 §8 이 #99 에 요구한 5종을 모두 채웠다.

| 요구 | 채운 방식 |
|---|---|
| confidence calibration | `calibrationPool` — 정답 라벨 + 난이도 4계층(easy/medium/hard/**trap**). gold 는 **confidence 값을 주지 않는다** — 주는 순간 곡선이 순환 논증이 된다. 오른쪽 꼬리는 trap 계층(산출하면 오답인 11건)이 결정한다 |
| 충돌 gold | 양성 2 · 음성 2. 음성은 양성과 **구조가 같고 값만 일치**한다 — 형태로 충돌을 탐지하는 구현이 걸린다 |
| 커버리지 gold | 질문 8개 × 5클래스 정답. `absent`(찾아봤는데 없다)와 `not_collected`(안 봤다)를 실제로 구분하는 질문을 포함 |
| abstention | 보류가 정답인 질문 4개 — 조건 1(근거 0건) · 조건 2(핵심 클래스 전면 부재) · 조건 3(**미해결** 충돌)을 모두 커버. **비보류가 정답인 4개**가 짝으로 있어 허위 보류도 측정된다 |
| 반대 증거 | Q2·Q3 에 `stance: contradicts` 근거가 실재한다 |

**충돌 양성 2건은 지어낸 것이 아니라 리포에 실재하는 모순이다** — §8 참조.

양성 2건은 **status 가 서로 다르다.** `CF1`(테이블 수 27 vs 28)은 둘 중 하나가 반드시 거짓이므로 `NEEDS_CHECK` 이고 보류를 유발한다. `CF2`(파싱 실패 보고)는 코드가 말하는 현행 동작과 ADR 이 말하는 계약 요구가 **둘 다 참**이므로 `COEXIST` 이고 보류 사유가 아니다(EVL §2.4 · §6.2 조건 3은 `NEEDS_CHECK` 에만 걸린다). 이 구분이 없으면 충돌 탐지가 보류 스위치로 전락한다 — 충돌이 보이면 무조건 보류하는 구현은 `CF2` 에서 **허위 보류**로 걸리고, 코드·테스트 2대1 다수결로 ADR 근거를 떨어뜨리는 구현은 **반대 증거 은폐**(A10·A14)로 걸린다. `COEXIST` 경로를 밟는 유일한 케이스이기도 하다.

수집 범위 전제(`collectionScope`)를 파일 첫머리에 못박았다. 실행이 그 범위를 만족하지 못하면 해당 클래스의 정답은 자동으로 `not_collected` 가 되고, **그 실행의 EVL 지표는 "측정 불가"로 기록**한다. 그중 하나는 지금 확정된 사실이다: `issue` 가 M0 내내 미수집이므로 **HISTORY intent 질문은 구조적으로 전부 보류가 정답**이다. 구현 실패가 아니라 수집 범위의 결과이므로 보류율 해석 시 반드시 분리한다.

## 4. 실패 재현 fixture · PII 코퍼스

### 4.1 실패 fixture (6건)

여기서 재는 것은 정확도가 아니라 **정직성**이다. 파싱을 못 하는 것은 baseline 이고, 못 했다는 사실을 말하지 않는 것이 실격이다(I1 §4.1).

| 종류 | DB | 코드 |
|---|---|---|
| 파싱 실패 | `db-broken-syntax.sql` | `code-broken-syntax.kt` |
| 미지원 문법 | `db-unsupported-trigger.sql` (트리거 + PL/pgSQL) | `code-unsupported-lang.scala` |
| 부분 추출 | `db-partial-extract.sql` (성공 2 · 실패 1 · 미지원 1) | `code-partial-extract.kt` |

- **부분 추출이 가장 중요하다.** 성공 건이 실제로 나오기 때문에 결과가 정상처럼 보이고, 나머지를 말하지 않으면 부분 성공이 완전 성공으로 위장된다.
- **R-F-4:** 실패 건수의 단위는 입력 문장 또는 파일이다. `;` 단순 분할로 한 문장이 여러 조각이 되어도 **1건**으로 센다. 분할 방식에 따라 실패율이 달라지면 실행 간 비교가 불가능하고, 그 자체가 결정성(H1) 위험 신호다.
- 현 `DdlParser.parse` 는 파싱 실패를 `catch { null } ?: continue` 로 삼키고(`DdlParser.kt#L18`), 그 동작이 테스트로 고정돼 있다(`DdlParserTest.kt#L44`). 이 픽스처들이 붉게 나오는 것은 **예상된 결과이며 픽스처의 오류가 아니다.**

### 4.2 PII·시크릿 코퍼스

전부 합성 값이다. 실존 인물·계정·자격증명이 아니며 실제 시스템에 사용해서는 안 된다.

- **양성 28건** — 주민등록번호·이름·이메일·전화·카드·계좌·주소·IP, 그리고 비밀번호·AWS 키·JWT·Slack/GitHub 토큰. 미마스킹 **1건이라도** 있으면 L0 실격이다(I1 §4.1 · H2).
- **음성 15건** — 마스킹하면 오탐인 값들. 오탐률은 게이트가 아니라 기록 대상이지만, 그중 **`GIT_SHA`(40자 hex)와 `CONTENT_HASH`(64자 hex)의 오탐은 별도 표기**한다: 이것들을 가리면 revision 추적(I1 §1.3)과 fixture hash 대조(§6)가 통째로 끊긴다.
- 세 가지 소스 형태(SQL·properties·log)를 둔 이유는 **로그가 가장 많이 미끄러지기 때문**이다. 로그 한 줄 안에 접속 URL(음성)과 password(양성)가 함께 있어, 줄 단위로 통째 마스킹하는 구현은 음성까지 삼킨다.

규칙이 예외를 던지면 **그 규칙의 실패로 기록하고 나머지 규칙을 계속 실행한다.** 예외가 그대로 올라가면 그 규칙의 결과뿐 아니라 뒤의 모든 규칙이 실행되지 않는데, 손상된 gold 일수록 예외가 잘 나므로 **가장 검사가 필요한 순간에 확인기가 침묵**하게 된다. 죽은 확인기의 침묵은 "문제 없음"과 구분되지 않는다.

> **모든 원본 대조는 고정 revision 의 blob 을 읽는다** — 작업 트리가 아니다(G5·G7·G8·G9 가 같은 로더를 쓴다). 확인기가 작업 트리를 읽으면 검사 결과가 체크아웃 상태에 따라 달라져, '검증 통과' 가 '고정 revision 과 일치' 를 뜻하지 않게 된다. 픽스처만 디스크에서 읽되 그 무결성은 G4 의 해시가 따로 보장한다.

`--rehash` 는 gold 를 의도적으로 고친 뒤 해시를 재고정하는 유지보수 명령이다. 검사 실패를 이것으로 덮으면 해시 고정이 하는 일이 없어진다.

## 6. 고정 (Pinning)

I1 §1.3 이 #99 로 위임한 **fixture hash 고정**을 여기서 완료한다. `manifest.json` 이 정본이다.

**revision 축이 둘이다:**

| 축 | 값 | 대상 |
|---|---|---|
| `sourceRevision` | `3c27259` | 코드·DB 원본, 테스트, E17 설계 문서 |
| `docsRevision` | `7d3db3e` | I1 기준선 계약 · EVL answer-shape 계약 · I3 Run Quality Report 계약 |

**왜 나눴나:** I1·EVL 계약은 `3c27259` **이후에** 작성돼 그 revision 에 존재하지 않는다. 한 revision 으로 우겨넣으면 그 좌표는 조회되지 않는 유령 좌표가 되고, EVL 충돌 케이스의 ADR 근거가 통째로 검증 불가가 된다. G5 가 각 소스를 **자기 revision 에서** 조회해 해시를 대조한다.

### 6.1 I3(#100)로 넘기는 두 값

I3 의 Run Quality Report 는 실행 하나당 **해시 하나**를 적는다(`run.fixtureHash`: `sha256:<64hex>` 또는 `UNPINNED`). 그런데 I2 가 고정하는 것은 픽스처 15개의 **개별** 해시다. 이 사이를 잇는 집계 규칙이 없으면 각 실행이 제멋대로 대표값을 골라 적게 되고, 그러면 `fixtureHash` 가 같다는 사실이 같은 입력이었음을 보장하지 못한다(I3 비교가능성 조건 2). 그래서 집계 규칙을 여기서 못박는다.

| 값 | 현재 | 계산 규칙 |
|---|---|---|
| `run.fixtureHash` | `sha256:42c7580540a7e988429e18138d7c3d1943a94e85e16705a6953872afde75ac93` | `"<경로> <sha256:…>"` 줄을 **경로 사전순** 정렬 → 개행으로 이음 → 끝에 개행 → sha256 |
| `evl.conflictDetection.goldSetId` | `gold-set/v0+a1a6d3dca210` | 위와 같은 방식으로 gold 파일 · 픽스처 · 고정 원본을 모두 이어 sha256, 앞 12자리 |

- **정렬을 규칙에 넣은 이유:** 파일 열거 순서는 파일시스템마다 다르다. 순서가 흔들리면 같은 픽스처가 실행마다 다른 해시를 낸다 — 결정성(I1 H1)의 문제다.
- **`goldSetId` 가 판정 규칙(스키마·확인기)까지 포함하는 이유:** 데이터가 같아도 규칙이 바뀌면 같은 산출물의 정오가 뒤집힌다. 규칙 변경이 신원에 드러나지 않으면 서로 다른 기준으로 잰 수치가 같은 `goldSetId` 아래 비교된다.
- 두 값은 **파생값**이며 손으로 적지 않는다. G4 가 재계산해 대조하고, `validate_gold.py` 는 실행할 때마다 두 값을 출력한다 — 보고서 작성자가 그대로 인용하면 된다.
- **위 표의 값이 낡으면 G4 가 실패한다.** 확인기가 이 문서를 읽어 현재 값과 대조하기 때문이다 — 문서에 옛 해시가 남아 있으면 보고서 작성자가 그것을 인용해 존재하지 않는 입력을 가리키게 된다. `goldSetId` 는 확인기를 고치기만 해도 바뀌는데, 그것이 의도다(판정 규칙 변경은 신원 변경이다).
- I3 §비교가능성은 `fixtureHash: UNPINNED` 인 실행을 baseline 으로 인정하지 않는다. **본 gold 가 승인되는 시점부터** 그 값이 위 해시로 바뀌며, 그때 비로소 `comparable=true` 인 실행이 가능해진다.

### 6.2 픽스처의 고정 방식

**픽스처는 revision 이 아니라 해시로 고정한다.** 픽스처는 이 gold 를 위해 합성한 것이라 리포 revision 과 독립적이며, 해시가 곧 정체성이다. 고정되지 않은 픽스처 파일이 `fixtures/` 아래 하나라도 있으면 G4 가 실패한다 — `fixtureHash: UNPINNED` 로 실행된 결과는 baseline 으로 인정하지 않는다(I1 §1.3).

## 8. 발견된 불일치 — I1 개정 안건

Gold 를 원본과 대조하는 과정에서 **개정이 필요한 항목 3건**을 찾았다. 그중 8.1·8.2 는 **리포에 실재하는 모순**이라 EVL 충돌 gold 의 양성 케이스로도 등재했고, 8.3 은 어휘의 공백이다. **세 건 모두 §7 의 승인 필수 검토 대상이다.** 본 문서는 이를 **기록하고 개정 안건으로 제기할 뿐, I1 을 임의로 고치지 않는다**(I1 §7: 개정은 리뷰어 승인 사항이며, 이전 값과 함께 남긴다 — P4 의 자기적용).

### 8.1 테이블 수: 27 vs 28 → `CF1.TABLE_COUNT`

I1 §1.1(L40)과 그 설명(L44)은 `CREATE TABLE` **28** 이라고 적었다. 고정 revision 원문의 실제 `CREATE TABLE` **문**은 **27건**이다.

28번째 `CREATE TABLE` 문자열 일치는 L221 의 한국어 주석이다:

```sql
-- 뷰 (DdlParser 는 CREATE TABLE 만 처리하므로 스킵되어야 함)
```

즉 I1 의 28 은 주석 한 줄을 센 grep 결과다. 공교롭게도 이 오탐은 gold 의 음성 항목 `L1.DB.TABLE.NEG.만` 과 **정확히 같은 실패**이며, 그래서 그 항목의 notes 에 출처로 적어 두었다.

- 테스트(`LegacySampleFixtureTest.kt#L18`)는 `>= 25` 만 단언해 중재하지 못한다.
- **제안:** I1 §1.1 을 `CREATE TABLE` 27 로 정정하고, §7 절차에 따라 이전 값(28)과 함께 개정 이력에 남긴다.
- 정정 전까지 이 충돌의 상태는 `NEEDS_CHECK` 이며, EVL Q2 의 정답은 **보류**다.

### 8.2 파싱 실패 보고: 현행 동작 vs 계약 요구 → `CF2.PARSE_FAILURE_REPORTING`

I1 §4.1(L169)은 "L1 무보고 파싱 실패 **0건**" 을 무조건 게이트로 못박았다. 그런데 현 구현은 실패를 조용히 삼키고(`DdlParser.kt#L18`), **그 동작이 테스트 이름으로 고정돼 있다**(`skips unparseable statements without failing`).

- 계약 위반은 아니다 — I1 은 앞으로 측정할 게이트를 선언한 것이고, 현행 동작은 아직 측정되지 않았다. 다만 **L0/L1 벤치가 시작되면 이 게이트에서 즉시 실패할 것이 지금 이미 확정적**이다.
- 코드와 테스트가 같은 편이라는 이유로 다수결로 닫으면 안 된다. 여기서 다투는 것은 사실이 아니라 **현행 동작과 계약 요구의 불일치**다.
- **제안:** #88 착수 전에 이 항목을 알려진 결함으로 등록하고, 실패 보고 경로 구현을 별도 이슈로 분리한다. 그러면 L0 벤치의 첫 결과가 "이미 알던 결함"과 "새로 발견한 결함"으로 구분된다.

### 8.3 L2 `method` 어휘에 코드용 값이 없다

`RelationKind` 는 `FK`/`NAMEPATTERN`/`AI`/`MANUAL` 네 값이다(I1 §6.1). 코드 트랙의 `override` 링크는 **명시 선언**이 근거인데 여기 대응하는 값이 없어 부득이 `FK` 로 적었다(`L2.CODE.OVR.*`).

- 이것은 gold 의 임시방편이지 정답이 아니다. `DECLARED` 같은 값을 추가하는 것이 옳다.
- **제안:** 어휘 추가는 계약 개정 사항이므로(I1 §6.2 · EVL §10.4) 리뷰어 판단으로 처리한다. 개정 전까지 gold 는 현 표기를 유지하고, 이 사실을 여기 남긴다.

| 실패 픽스처 보고 좌표 **8건 중 3건**이 파일 범위 밖 (`#L3-L8` ↔ 7행 파일 등) | 유령 좌표 | 3건 정정 |

**왜 통과했었나 — 확인기의 사각지대 두 곳:**

1. **G9 가 `expect != PRESENT` 항목을 통째로 건너뛰었다.** 그래서 음성·제외 항목의 좌표는 한 번도 원본과 대조되지 않았다. 이제 **모든** 항목의 좌표가 빈 줄이 아닌 실제 내용을 가리키는지 보고, 실재하는 것(PRESENT·REPORTED_EXCLUDED)은 이름 대조까지 한다. `ABSENT` 는 정의상 원본에 없으므로 이름 대조를 요구할 수 없어 빈 줄 검사까지만 한다 — 그래도 "왜 그것이 오탐인지" 를 가리키는 좌표는 실재해야 한다.
2. **G14 가 실패 픽스처의 `reported[].locator` 를 검사하지 않았다.** L1·L2·PII 좌표는 전부 G7~G9 가 보는데 실패 보고 좌표만 빠져 있었다. 정답이 존재하지 않는 행을 가리키면 채점자는 대조할 대상이 없어 그 항목을 통과 처리하게 된다.

정정 후 각 결함을 되돌려 **이제는 검출되는지** 확인했다(5종 전부 `[G9]`·`[G14]` 로 검출). 이 두 사각지대는 3차 외부 리뷰의 LOD-037(작업 트리 vs 고정 blob)과 같은 계열이다 — **"검사하지 않는 것" 과 "검사해서 통과한 것" 이 같은 `OK` 로 보였다.**

## 16. 자체 리뷰 2차 (2026-07-30 · 로컬)

1차 자체 리뷰에서 유령 좌표가 나온 원인을 좇았다. 원인은 개별 실수가 아니라 **구조**였다.

**좌표의 *내용* 검증은 `db.json`(G9)과 `pii.json`(G8)에만 있었다.** `l1/code.json`·`l2/links.json`·EVL 근거는 G7 의 **범위 검사만** 받았다 — 행 번호가 파일 안에 있기만 하면 통과했다. 지난 두 라운드의 결함이 모두 "내용을 안 보는 곳"에서 나온 것은 우연이 아니다.

그 가정을 실제로 확인했더니:

| 대상 | 결과 |
|---|---|
| `l2/links.json` 의 ref **65건 중 42건**이 실제 내용과 어긋남 | 손으로 적은 좌표가 계통적으로 1~2행씩 밀려 있었고, 일부는 **빈 줄**을 가리켰다. 예: `TB_ORD_HD.CUST_NO` 는 L82 인데 L80(테이블 선언 줄)을 가리킴 |
| `l1/code.json` | 이상 없음 — 전 항목의 심볼 이름이 인용 구간에 실재 |
| EVL `requiredEvidence` | 이상 없음 — 8개 질문의 근거 좌표가 모두 정확한 내용을 가리킴 |

**구조적 수정:** L2 좌표를 손으로 적는 것을 그만두고 **L1 gold 에서 유도**하게 했다. 각 `refs[]` 에 `endpoint`(가리키는 대상)를 두고, 그것이 gold 항목 id 면 **그 항목의 `locator` 와 같아야 한다**(G10). 이제 L1 좌표가 정정되면 L2 가 따라오지 않는 것 자체가 실패로 잡힌다.

> **왜 이게 중요한가:** L2 링크 gold 는 "이 두 관측이 같은 것을 가리킨다" 는 주장이다. 그 주장의 좌표가 엉뚱한 행이면 채점자가 무엇을 대조해야 하는지 알 수 없고, **틀린 좌표를 근거로 링크를 맞다고 판정**하게 된다. I1 §6.1 이 "근거는 원본에서 재확인 가능한 좌표를 가져야 한다" 고 못박은 바로 그 지점이다.

회귀 증명 4종을 확인했다 — 좌표를 원래의 틀린 값으로 되돌리기 · `endpoint` 제거 · `endpoint` 와 대상 불일치 · **L1 만 고치고 L2 를 안 고친 경우**, 전부 `[G10]` 으로 검출된다.

### 남은 사각지대 (정직한 기록)

- `l3/claims.json` 은 좌표를 갖지 않는다(시나리오이므로). 그 대신 참조하는 gold id 가 실재하는지는 검사하지 않는다 — `mustHold` 문장 안의 id 는 산문이라 기계로 읽지 않는다. **L3 채점 시 사람이 대조해야 한다.**
- `failures.json` 의 `extracted[]`(성공해야 하는 추출 결과)는 픽스처 내용과 대조되지 않는다. 보고 좌표(G14)와 달리 이건 구조화된 값이라 대조 규칙을 세울 수 있으나, 그러려면 SQL·Kotlin 파서가 필요해 확인기의 범위를 넘는다 — **#88~#91 채점기가 맡을 몫**이다.
