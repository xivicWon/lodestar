## 1. 무엇을 어떻게 쟀는가

### 1.1 측정 대상 — 이 리포에 실재하는 L0 수집 경로

| 트랙 | 수집기 | 입력(고정) | 산출물 |
|---|---|---|---|
| **db** | `DdlParser` + `DdlSource` (DDL 텍스트 경로) · `SampleLegacyDb` + `MetadataService` (샘플 적재 경로) — **두 경로를 각각 3회 실행해 따로 쟀다**(§7 V11) | `backend/src/main/resources/com/ontostudio/rdb/legacy-sample.sql` @`3c27259` (`sha256:b8f5…0e94` · 262행) | `SchemaModel` (테이블·컬럼·PK·FK) |
| **code** | `lodestar_codegraph` (walk → tree-sitter → extract → resolve → cluster → emit) | `backend/src/main/kotlin` @`3c27259` (`.kt` 59개) | `codegraph.json` (노드·엣지·군집) |

두 트랙은 **분리 산출**한다 — 합산 평균은 실패를 가린다(I1 §4.2 · I3 §1).

### 1.2 측정 규칙 (선언 — 프로브 코드에 같은 ID 로 박혀 있다)

| ID | 규칙 |
|---|---|
| **M-DB-1** | 입력 단위는 **SQL 문장**이다. `;` 로 나눈 뒤 `--` 주석 행을 걷어내고 남은 비어있지 않은 조각 하나가 1건이다(I2 R-F-4). 좌표는 그 문장의 **첫 실제 코드 행**을 가리킨다. 이 규칙은 PL/pgSQL 본문이 없는 입력에서만 정확하므로 **전제를 테스트가 직접 확인한다**(`pinned input has no nested statement bodies`) |
| **M-DB-2** | 수집 성공(ACQUIRED) = 그 문장의 대상이 수집기 산출물에 나타난 것 |
| **M-DB-3** | `CREATE VIEW` = 미지원 제외, `INSERT` = L0 최소저장 원칙상 범위 밖 제외. **둘 다 사유와 함께 보고되어야 하는 제외다** |
| **M-DB-4 · M-CODE-2** | 결정성 = 3회 실행 산출물 해시의 **최대 동일 그룹 크기 / 3** |
| **M-CODE-1** | 입력 단위는 **파일**이다. 수집 범위 루트 아래 모든 정규 파일이 분모이며, 확장자 필터로 걸러진 파일은 사유와 함께 보고되어야 하는 제외다 |
| **M-CODE-3** | provenance 는 필수 5필드(`projectId`·`sourceId`·`revision`·`contentHash`·`collectorVersion`)가 **소스 단위로** 산출물에서 조회되는지로 센다. 동등 식별자는 프로브에 선언된 별칭표로만 인정하고 인정 근거를 함께 남긴다 |

**`counts.input` 에 설계상 정당한 제외까지 넣은 이유:** I3 R20 은 `scopeCoverage = output/input` 을 고정하고
제외를 분모에 남긴다. 행 데이터 제외는 정당하지만, 정당한 제외도 **사유와 좌표를 말하지 않으면 조용한 스킵**과
구별되지 않는다. 커버리지가 낮게 보이는 쪽을 택했다 — 유리하게 읽히는 분모를 고르는 것이 이 계약이 막으려는 것이다.

**애매한 게이트는 HALT 로 읽었다.** I1 §3.2 는 "등급 판단이 애매하면 HALT 로 처리한다. 통과 쪽으로 기우는
해석은 금지" 라고 못박았다. 보안 게이트가 그 자리다(§4 F7).

### 1.3 증거의 사슬

```
고정 입력(해시 대조)  →  실제 수집기 실행  →  프로브 산출물(결정적 JSON)  →  Run Quality Report v0
                                                    │                          │
                                        표류 시 테스트/‑‑check 실패      프로브의 순수 함수(V2)
```

- DB 프로브는 백엔드 테스트가 겸한다(`L0DbSourceProbeTest`) — 커밋된 산출물과 다르거나 **없으면** 테스트가
  붉어진다. 증거 디렉토리를 `tasks.test` 의 입력으로 선언해 두었다 — 그러지 않으면 gradle 이 증거 변경을
  모른 채 `UP-TO-DATE` 로 검사를 건너뛴다(검사를 건너뛴 그린은 그린이 아니다).
- 코드 프로브는 `probe_code.py --check` 가 같은 일을 한다.
- 보고서는 프로브에서 결정적으로 파생되므로 **수치를 손으로 고치면 확인기가 잡는다**(§7 V2).
- 재현 절차: [`bench/l0/README.md`](bench/l0/README.md).

## 4. 발견

### F1 [H1] 코드 수집기의 산출물이 재현되지 않는다

동일 입력·동일 revision 3회 실행이 **세 번 모두 다른 산출물**을 냈다.

- 갈라지는 지점: `nodes[].community` · `meta.community_count`. 노드·엣지·좌표는 동일하다(구조 해시 고정).
- 원인: `cluster.annotate` 가 `ids = {n.id for n in nodes}`(집합)을 그대로 `g.add_nodes_from(ids)` 에 넘긴다
  (`codegraph/src/lodestar_codegraph/cluster.py:8`). 문자열 해시 랜덤화로 집합 순회 순서가 프로세스마다
  달라지고, Louvain 은 노드 순서에 의존하므로 **`seed=42` 를 고정해도** 군집 배정이 갈린다.
- 통제 실험(증거): `PYTHONHASHSEED=0` 두 번은 동일, 시드를 `1` 로 바꾸면 달라진다
  (`probe-code.json#determinismRootCause`). 즉 이 수치는 재실행 시 우연히 `0.6667` 로 보일 수 있어도
  **"재현 보장 없음" 이라는 사실은 바뀌지 않는다.**
- 폭발 반경: 사실 자체가 아니라 사실에 붙는 **군집 라벨**이 흔들린다. 그래도 게이트는 산출물 단위이며,
  하류가 `community` 를 읽는 한 상위 결과가 실행마다 달라진다.

### F2 필수 식별 필드가 없다 — 추적도 신선도 산출도 불가

| 필드 | db | code |
|---|---|---|
| `projectId` | 없음 | 없음 |
| `sourceId` | 없음 | `nodes[].path` (경로 — 안정 id 아님) |
| `revision` | 없음 | 없음 |
| `contentHash` | 없음 | 없음 |
| `collectorVersion` | 없음 (수집기가 버전을 선언하지 않음) | `meta.generated_by` = `"lodestar-codegraph v1"` (커밋·semver 없음) |

`revision` 과 수집 시각이 없으므로 **신선도 지표를 산출할 방법이 없다** — "이 산출물이 어느 시점의 원본을
본 것인가" 를 산출물만으로 답할 수 없다. 이번 벤치가 revision 을 아는 것은 프로브가 밖에서 붙여줬기 때문이다.

### F3 오류 가시성 0% — 실패·제외를 실을 자리가 없다

- db: `DdlParser.parse` 의 반환형은 `SchemaModel` 뿐이다. 실패·제외를 담을 필드가 **구조적으로 없다**
  (`DdlParser.kt:18` 의 `catch { null } ?: continue`). 보고해야 할 14건(범위 제외 9 + 픽스처 5) 중 0건 보고.
- db(JDBC 메타데이터 경로): `MetadataService` 는 `getTables(..., arrayOf("TABLE"))` 로 뷰를 타입 필터로
  걸러낸다(`MetadataService.kt:21`). `VW_ORD_SUMMARY` 가 산출물에 없고 제외 사유도 없다 — **DDL 텍스트
  경로와 같은 조용한 제외가 두 경로에서 독립적으로 재현됐다.**
- code: `meta.skipped` 는 **건수만** 있고 대상·사유가 없다. 픽스처 3건 중 0건 보고.
- 이것은 I2 §8.2 가 "#88 착수 전에 알려진 결함으로 등록하자" 고 제기한 항목의 **실측 확인**이다.

### F4 조용한 부분 복구 — 실패한 테이블을 반쯤 살려 성공으로 낸다

`db-partial-extract.sql` 의 `TB_BAD_MIDDLE` 은 쉼표 누락으로 파싱 실패해야 하는데, 수집기는
**`TB_BAD_MIDDLE(columns=BAD_ID)`** 를 산출했다 — `BAD_NM` 은 조용히 사라졌고 실패 보고도 없다.
I2 gold 가 "조용한 부분 복구는 조용한 스킵과 같은 종류의 거짓말" 이라며 오답으로 규정한 바로 그 경로다.

### F5 확장자 필터의 조용한 제외 — `not_collected` 와 `absent` 가 L0 에서 무너진다

`code-unsupported-lang.scala` 는 `walked=0` 이며 산출물에 **흔적이 전혀 남지 않는다**
(`lang.py#lang_for_path`). "수집 범위 밖" 과 "수집했는데 없음" 이 구분되지 않으므로,
EVL 계약 §2.5 의 `not_collected` / `absent` 구분이 최하층에서 이미 성립하지 않는다.

### F6 부분 성공이 완전 성공으로 표기된다

`code-broken-syntax.kt` · `code-partial-extract.kt` 모두 `parsed == walked` (전량 성공)로 표기됐다.
tree-sitter 는 오류 복구 파서라 깨진 입력에서도 트리를 만들고, 산출물에 **ERROR 노드의 존재가 실리지 않는다**.
`code-broken-syntax.kt` 는 심볼 0개이면서도 파일 노드가 성공으로 등재됐다.

### F7 [H2] 마스킹 단계가 없고, 샘플 적재 경로는 행 데이터를 원문으로 저장한다

- 마스킹 구현 탐색 결과 **0건** (`backend/src/main` · `codegraph/src` · `frontend/src`).
- gold 양성은 db 14건 / code 28건 모두 **마스킹 0건**이다. 산출물에 원문이 남지 않은 것은 마스킹이 아니라
  **미수집(not_collected)** 때문이다 — db 는 `INSERT` 를 버리고, code 는 코퍼스 확장자를 walk 하지 않는다.
- 그러나 `SampleLegacyDb.open()` 은 `CREATE` 뿐 아니라 **`INSERT` 까지 전 36문장을 실행**한다
  (`SampleLegacyDb.kt:20`). 적재 후 질의로 **미마스킹 PII 형태 값 14건**을 회수했다
  (`TB_CUST_MST.RPRS_NM`·`TEL_NO`·`BIZ_NO`·`CUST_NM`, `TB_EMP_MST.EMP_NM` — 좌표
  `legacy-sample.sql#L229-L262`, 값은 보고서에 적지 않았다). 이것은 동시에
  **"기본 저장은 최소 메타데이터·구조 정보로 제한" 요구의 위반**이다.
- 같은 경로의 **수집 산출물**(`MetadataService.extract`)에는 행 값이 실리지 않았다 — 적재된 14개 값 중
  산출물로 새어 나온 것은 0건이다. 노출 지점은 산출물이 아니라 **적재된 저장소 그 자체**이며, 두 지점을
  구분해 기록한다.
- 판정: 마스킹 단계가 존재하지 않는 상태에서 "미마스킹 0건" 을 통과로 읽는 것은 통과 쪽으로 기운 해석이다.
  I1 §3.2 에 따라 **FAIL · H2** 로 처리했다.

### F8 [gold 공백] 수집되는 표면에 PII 양성이 없어 code 트랙 마스킹은 측정 불가

gold v0 의 양성 **28건**(전체 항목 44건 = 양성 28 + 음성 16)은 전부 `.sql`·`.properties`·`.log` 에 있다. 코드 수집기가 실제로 읽는 확장자
(`.kt`·`.java`) 안에 양성이 없어, **수집된 표면에서의 마스킹 동작은 이 gold 로 측정할 수 없다.**
픽스처를 여기서 임의로 만들지 않았다 — gold 는 승인된 정답셋이므로 개정 절차를 따른다(§8.2).

### F9 [계약 공백] 메타데이터·오류 가시성 실패에 대응하는 HALT 등급이 없다

I1 §4.1 은 L0 메타데이터 완전성 100% 와 오류 가시성 100% 를 **무조건 게이트**로 선언했는데,
§3.2 의 중단 규칙 H1~H5 에는 그 두 실패에 대응하는 항목이 없다(H2 는 "결정성·보안" 만 든다).
이번 판정은 §3.2 의 "애매하면 HALT" + G4(부분 통과 금지)로 **BLOCKED** 로 처리했고,
`haltRules` 에는 실제로 대응하는 H1·H2 만 적었다. 어휘를 열지 않았다 — 개정 안건으로 남긴다(§8.1).

### F10 [부수 확인] `CREATE TABLE` 은 27건이다

독립 인벤토리(M-DB-1)로 센 결과 `CREATE TABLE` **27** · `CREATE VIEW` 1 · `INSERT` 8 = 36문장이다.
I1 §1.1 의 "28" 은 주석 한 줄을 센 grep 결과라는 I2 §8.1 의 지적이 **실측으로 확인**됐다.

## 7. 증거 적합성 확인기 (V1~V11)

## 8. 계약 개정 안건 (@xivicWon 승인 사항)

I2 §8 과 같은 성격이다. **기록하고 제기할 뿐, 계약을 임의로 고치지 않는다.**

### 8.1 I1 §3.2 — 메타데이터·오류 가시성 실패에 대응하는 HALT 등급이 없다 (F9)

§4.1 이 무조건 게이트로 선언한 두 항목이 §3.2 의 어느 등급에도 매핑되지 않는다. 지금은 "애매하면 HALT"
로 처리되지만, 그 해석에 의존하면 **게이트를 통과 못 한 실행이 등급 어휘의 공백을 타고 새어나갈 수 있다.**

- **제안:** H2 의 문구를 "L0 결정성·보안" 에서 "L0 무조건 게이트 중 하나라도 미통과" 로 확장하거나,
  `H6`(추적 불가) · `H7`(오류 은폐)을 추가한다. 어휘 확장은 `schemaVersion` 상향 사유이므로(I3 §7.3)
  I3 스키마의 `haltRules` enum 개정이 함께 필요하다.

### 8.2 I2 gold — 수집되는 확장자 안에 PII 양성이 없다 (F8)

- **제안:** `.kt` 안에 하드코딩 시크릿(예: `const val TOKEN = "ghp_…"`)을 담은 양성 픽스처 1건과,
  마스킹하면 오탐인 음성(상수명에 `secret` 이 들어가지만 값은 비밀이 아닌 것) 1건을 추가한다.
  gold 개정이므로 `--rehash` 후 G1~G14 재통과와 승인이 필요하며, **개정되면 이번 code 트랙 보안 수치는
  비교 기준선에서 제외**된다(I2 §10.4).

### 8.3 I1 §1.1 — `CREATE TABLE` 28 → 27 (F10)

I2 §8.1 의 제안을 실측으로 확인했다. 정정 시 이전 값(28)을 개정 이력에 함께 남긴다(I1 §7.3).

## 10. 리뷰 반영 이력 (2026-07-30 · PR #111)

AI 코드리뷰의 확인 질문 10건을 검토했다. **확정 이슈는 0건**이었으나 질문 중 **9건이 실제 결함**이었고
모두 고쳤다. 1건은 답변으로 닫았다. 계측기가 바뀌었으므로 두 프로브를 재실행해 증거를 갱신했다
(병합 전 같은 측정 세션이라 runId 는 유지했고, 보고서 수치는 변하지 않았다).

| 지적 | 판단 | 조치 |
|---|---|---|
| `MetadataService` 를 호출하지 않고 `COUNT` 만 질의해서 "샘플 적재 경로 실측" 이라 했다 | **타당 — 가장 중요했다** | 선언한 두 수집 경로 중 하나를 재지 않고 주장에 넣었다. `MetadataService.extract(conn)` 를 3회 실행해 산출 테이블·뷰 처리·FK·결정성·provenance·행 값 누출을 따로 쟀다. 그 결과 **뷰의 조용한 제외가 두 경로에서 독립적으로 재현**됨을 확인했다(F3). 재발 방지로 **V11**(선언 경로 계측 완비)을 신설했다 |
| 커밋된 `probe-db.json` 이 없으면 테스트가 비교를 생략하고 통과한다 | **타당** | 증거가 없으면 실패한다. 새 runId 최초 생성만 `-DL0_PROBE_BOOTSTRAP=true` 로 1회 우회하며 그 흔적은 diff 에 남는다. **추가로 발견한 더 큰 구멍**: gradle 은 `docs/` 를 입력으로 몰라 증거가 바뀌어도 UP-TO-DATE 로 검사를 건너뛴다 — `tasks.test` 에 증거 디렉토리를 입력으로 선언해 막고, 삭제·변조 두 경우 모두 `--rerun-tasks` 없이 실패함을 확인했다 |
| `build_report.py` 가 기존 보고서를 무조건 덮어쓴다 | **타당** | 재생성 결과가 커밋된 보고서와 다르면 쓰지 않고 실패하며, 새 runId 를 요구한다(I3 §5.5). 실제로 수치를 바꿔 넣어 차단을 확인했다 |
| `probe_code.py --check --out <기준파일>` 로 기준을 갱신한 뒤 자기 자신과 비교하는 우회가 가능하다 | **타당** | 기준 증거를 **쓰기 전에** 읽고, `--out` 이 기준 파일을 가리키면 거부한다 |
| `pinnedSources` 가 범위의 일부만 고정하므로 `allPinnedMatch` 로는 입력 신원이 보장되지 않는다 | **타당** (다만 "누락 시 true 가 된다" 는 전제는 사실과 다르다 — 누락 파일은 `None ≠ hash` 로 이미 불일치로 잡혔다) | 지적의 본질이 맞다: gold 는 59파일 중 7건만 고정한다. 범위 **전 파일을 고정 revision blob 과 대조**하고 경로 집합까지 양방향으로 본다(59/59 일치). V3 가 이를 강제한다 |
| `pii.positives` 28 과 `goldGap` 의 "양성 44건" 이 어긋난다 | **타당 — 문서 오류였다** | gold 는 양성 28 + 음성 16 = 항목 44 다. 프로브 문구와 본문 F8 을 정정했다 |
| 결정성 FAIL 인데 `coverageClasses.code.deterministic` 이 `true` 다 | **타당** | 두 문제가 있었다. ① 의미: 이 필드는 **state 의 3회 안정성**(EVL §7.1)이고 산출물 결정성이 아니다 — §3.2 에 규범 필드가 무엇인지 명시했다. ② 근거: 그런데도 값을 **하드코딩**하고 있었다. 프로브가 3회 실행에서 state 를 재고 보고서가 그것을 옮겨 적도록 바꿨다 |
| V6 이 픽스처 `id` 의 존재만 보고 등록된 경로·해시와의 귀속을 보지 않는다 | **타당** | id ↔ 경로 ↔ 해시 ↔ 기대 보고 건수의 귀속을 gold 선언과 대조한다. `id` 를 바꿔 붙이는 결함 주입 케이스를 추가했다 |
| README 의 `cd backend && … && cd ..` 는 gradle 실패 시 디렉토리가 어긋난다 | **타당** | 서브셸로 격리했다 |
| V8 이 세 판정을 정확히 `Lab` 으로 강제하지 않고 `Retire` 를 허용한다 | **의도된 설계** | 확인기는 **계약 규칙**을 강제하고 **판정 내용**은 강제하지 않는다. `Lab` 세 건은 이 실행의 판정이지 계약이 아니다 — 승인권자(@xivicWon)나 I4(#101)가 근거를 보고 `Retire` 로 바꿀 수 있어야 하고, 그때 확인기가 거부하면 확인기가 판정 권한을 침범한다(I1 §1.2). 대신 **넘을 수 없는 선**은 전부 검사한다: 측정 없는 Core 금지 · 게이트 실패 실행의 Core 금지 · 근거 링크 필수 · 측정한 수집기의 판정 누락 금지 |

확인기 규칙이 1개(V11), 결함 주입 케이스가 4개 늘었다(20 → 24케이스 · V1~V11).

## 11. 한계

- **자기참조:** 대상은 Lodestar 한 앱이다. 다른 성격의 프로젝트로 일반화하지 않는다(I1 §1.4).
- **code 트랙 결정성 수치의 성질:** `0.3333` 은 이번 3회 실행의 관측이다. 재실행 시 우연히 `0.6667` 이 될 수
  있으나 "재현 보장 없음" 은 시드 통제 실험으로 고정돼 있다(F1).
- **db 트랙 문장 인벤토리:** M-DB-1 은 PL/pgSQL 본문이 없는 입력에서만 정확하다. 고정 입력에 그런 본문이
  없다는 전제를 테스트가 확인하지만, 다른 입력에 그대로 적용할 수 없다(I2 R-F-4 의 함정).
- **측정하지 않은 것:** 라이브 JDBC 수집 경로(`LiveJdbcSource`)는 외부 DB 가 필요해 이번 범위에서 제외했다.
  미측정은 통과가 아니며, 그 경로를 근거로 어떤 주장도 하지 않는다.
